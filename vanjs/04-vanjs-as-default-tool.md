# 我为什么可以把 VanJS 当作常用工具

这篇不是 VanJS 教程，也不是框架横评。

它记录的是一次慢慢想清楚的过程：如果工作需要 React，临时去用、配合 AI 去写就够了；那么属于自己的项目，究竟有没有必要继续背着主流框架的整套复杂度？

最后的答案是：没有。

而且 VanJS 并不是一个只能拿来学习的小玩具。对我真正会写的那些程序来说，它完全可以成为常用工具。

## 从 React 的问题开始

最开始的想法是：个人项目也尽量靠近 React，这样经验可以迁移到工作。

这个想法当然合理，但里面藏着一个前提：好像不沿用 React 的组件、hooks、虚拟 DOM 和生态，个人项目积累的经验就浪费了。

其实不是。

真正能迁移的东西是：

```text
JavaScript
DOM 和事件
HTML 与 CSS
网络、缓存和存储
状态建模
数据流
副作用边界
可访问性
性能判断
调试能力
```

React 的 API 和约定只是其中一层，而且还是需要工作时可以临时补起来的一层。

如果有 AI 帮忙查 API、补样板代码，熟悉 React 语法的成本进一步降低了。相比之下，对浏览器本身的理解没有办法用背几个 hooks 来替代。

所以方向逐渐变成：

> 工作需要什么就用什么；自己的东西，用自己真正喜欢、能够看穿的工具。

## VanJS 牛就牛在它只有一百多行

VanJS 最吸引人的地方不是 benchmark，也不是“1KB 框架”这个标签，而是它真的小到可以读完。

```text
van.tags   创建真实 DOM
van.add    添加节点
van.state  保存响应式状态
van.derive 建立派生和副作用
binding    把状态变化连接到 DOM
```

它没有试图创造一个与浏览器平行的世界。

写：

```js
const node = div(
  button("Hello"),
)
```

拿到的就是一个真正的 `HTMLDivElement`。

可以马上：

```js
node.append(...children)
node.querySelector("button")
node.addEventListener("click", handler)
node.style.setProperty("--color", color)
node.animate(keyframes, options)
```

不需要 ref，不需要 escape hatch，也不需要先确认框架是否允许。

这意味着 VanJS 并没有把原生 JS 藏起来。它只是把最机械、最重复的 DOM 创建和状态绑定变得好写。

这种抽象很薄，所以用了它反而会继续学习 DOM，而不是远离 DOM。

## 类似的小框架当然还有很多

Sinuous 可以看另一种细粒度响应式；uhtml 可以看 tagged template 和动态槽位；Hyperapp 可以看一千字节左右怎样实现虚拟 DOM 与单向数据流；Mithril 可以看一个小而完整的 SPA 框架。

它们都值得读。

但“值得读”不等于“都值得换过去”。

Mithril 一开始不容易看懂，是因为它和 VanJS 并不是同一种东西：

```text
VanJS：
状态改变
→ 找到相关 binding
→ 更新对应的真实 DOM

Mithril：
状态改变
→ 重新执行 view
→ 生成新的虚拟 DOM
→ 和旧虚拟 DOM 比较
→ 再修改真实 DOM
```

Mithril 的优雅是“小而完整”；VanJS 的优雅是“小到仍然几乎就是浏览器”。

我现在更喜欢后者。

所以这些框架更适合成为研究材料：看看同一个问题还能怎样解决，然后回来更清楚地理解 VanJS 的选择。没有必要把每次理解一种新设计，都变成一次技术栈迁移。

## 正经项目真的需要大框架吗

“小框架适合 demo，大框架才适合正经项目”听起来很自然，但仔细想想，它把几种完全不同的东西混在了一起。

大框架解决的往往不只是 UI 表达能力，还包括：

```text
大量工程师共享同一种语言
招聘和人员流动
跨团队规范
现成组件和供应商支持
大型组织中的一致性
多年历史需求的兼容
```

这些价值都是真的。

但它们是生态价值和组织价值，不等于一个普通 Web 界面在技术上必须那么复杂。

对个人项目来说，更现实的问题是：

```text
我能不能快速表达想法？
半年后还能不能看懂？
出了问题能不能一路追到底？
某个局部变复杂时能不能单独替换？
依赖消失后我有没有能力接管？
```

在这些问题上，一个一百多行、返回真实 DOM 的工具，可能比一个无所不包的平台更稳。

## 对“大型前端”的祛魅

X、小红书、抖音看起来是巨型产品，但如果只看普通客户端界面，其基本模型并没有多神秘。

```text
获取数据
展示列表
打开详情
点赞、评论、收藏
发布内容
上传图片或视频
继续分页
接收通知
```

前端代码当然会很多，但代码量大不等于技术本质复杂。

它们的规模往往来自：

```text
页面和业务种类很多
产品规则持续累积
广告、埋点、实验和风控
多端与历史兼容
异常情况全部要处理
大量细节反复打磨
```

这是一种数量复杂度和组织复杂度。

真正困难的部分往往还在 UI 框架之外：

```text
推荐系统
内容审核
大规模缓存
搜索和排序
图片与视频转码
CDN 和弱网优化
推送与消息系统
账号安全和反滥用
百万用户下的数据一致性
```

React、Vue、VanJS 都不会自动解决这些问题。

抖音式页面在 UI 上甚至可以很简单：一个全屏 `<video>`、几个按钮、上下切换和评论面板。真正难的是首帧时间、预加载、自适应码率、转码、CDN、直播与弱网恢复。

小红书式页面也无非是瀑布流、详情、图片轮播、搜索、评论和发布器。真正困难的图片处理、上传恢复、推荐和审核仍然是独立子系统。

所以不能看到一个世界级产品，就反推出它的每个页面都需要世界级复杂的 UI 框架。

## 真正变态的前端是什么

另一类程序确实在客户端本身就非常复杂：

```text
Figma
Photoshop Web
OnlyOffice
IDE
CAD
专业音视频时间线
大型低代码画布
三维编辑器
```

这里会出现：

```text
无限画布和坐标系统
精确命中测试
图层与选区
撤销、重做和操作历史
专业排版与字体
GPU 渲染
大型文件格式
CRDT 与多人实时协作
编译器或语言服务
```

但这类复杂度也不是换成 React 就解决了。

真正的核心通常是：

```text
Canvas / SVG
WebGL / WebGPU
WebAssembly
Web Worker
CRDT
专业渲染引擎
领域算法
```

UI 框架可能只负责工具栏、菜单、弹窗和属性面板。

更重要的是：我大概率不会独自去写一个 Figma、Photoshop 或 Office，即使真的有一天要写，也不值得今天所有普通页面提前承担那种复杂度。

> 不要为了一个大概率永远不会出现的极端未来，让今天的每个普通项目都预付架构成本。

这就是最重要的祛魅。

## VanX 已经补上了复杂列表

如果只拿 VanJS Core 中一个返回整棵列表的 binding 去和其他框架比较，会低估完整的 VanJS 方案。

VanJS 有意保持核心很小，而把复杂响应式数据和列表放在官方扩展 VanX：

```text
vanX.reactive  深层响应式对象
vanX.list      响应式列表
vanX.replace   批量更新、插入、删除和重排
vanX.calc      计算字段
vanX.compact   序列化前整理数据
```

所以实际分工是：

```text
普通组件和局部状态
→ VanJS

复杂对象、keyed list、排序和批量替换
→ VanX

动画、拖拽、画布等高频热点
→ 原生 DOM / Canvas / SVG / WebGL

图表、地图、编辑器和媒体
→ 专业库
```

复杂列表并不要求换掉整套技术。

VanX 本身仍然很小。VanJS 没把列表算法硬塞进百行核心，不是它不知道列表存在，而是它选择让基础能力和进阶能力保持分层。

## 性能上不必神化，也不必担心

VanJS 不需要在每张 benchmark 表上都拿第一，才能成为一个好工具。

Solid、Svelte 之类可以借助编译器生成更专门、更精确的 DOM 更新代码；Sinuous、uhtml 对复杂 DOM range 和列表更新也有自己的优化。某些大型列表测试中，它们可以比 VanJS 更快。

但 VanJS 的性能优势是另一种东西：

```text
运行时极小
启动成本低
局部依赖直接
更新过程容易理解
遇到热点可以立即回到原生实现
```

例如拖拽过程不必每一帧都进入响应式系统：

```js
element.onpointermove = event => {
  element.style.transform =
    `translate3d(${event.clientX}px, ${event.clientY}px, 0)`
}
```

结束时再把有业务意义的结果写回状态即可。

Canvas 也可以直接作为真实节点交给专业代码：

```js
const canvasDom = canvas()
const context = canvasDom.getContext("2d")
```

这里没有框架所有权障碍。VanJS 创建的 DOM 本来就是自己的 DOM。

因此更准确的说法不是“VanJS 永远最快”，而是：

> VanJS 的默认性能足够好，性能行为足够透明，而且逃回理论最优原生实现的路非常短。

对于真正理解浏览器的人，这往往比综合 benchmark 第一名更有价值。

## 专业问题就应该用专业库

喜欢自己研究实现，不等于什么都必须自己造。

有些领域的复杂度是真实的，而且已经积累了大量专业知识：

```text
图表       ECharts / D3
地图       MapLibre
代码编辑器 CodeMirror
富文本     ProseMirror 等编辑器核心
音视频     原生媒体 API 与专业播放库
```

合理的原则不是“零依赖”，而是：

> 普通能力保持简单透明；专业领域尊重专业积累。

VanJS 很适合做这些库的外壳。它管理页面、状态、按钮和面板；专业库独占自己的 DOM 容器。

只要明确所有权即可：

```text
VanJS 管容器以及外围 UI
专业库管容器内部
```

不要让两个系统同时增删同一块 DOM，就不会产生结构性冲突。

## 所谓“正经项目”，稳的是边界，不是框架尺寸

VanJS 不会强迫项目形成结构，所以自己要主动保持边界。

```text
domain/
  纯业务逻辑，不知道 VanJS、DOM、fetch

services/
  HTTP、IndexedDB、上传、WebSocket

stores/
  VanJS/VanX 状态和业务动作

ui/
  页面、组件、DOM binding
```

最重要的是让业务核心保持普通 JavaScript：

```js
export function toggleTodo(todo) {
  return {
    ...todo,
    done: !todo.done,
  }
}
```

外面再接响应式状态：

```js
function handleToggle(id) {
  todos[id] = toggleTodo(todos[id])
}
```

这样真正决定项目寿命的代码属于自己。VanJS 是薄薄的 UI 层，不会渗进所有业务规则。

如果未来真的换技术：

```text
domain    不用改
services  基本不用改
stores    少量调整
ui        重新表达
```

这比寄希望于任何框架永远不变更可靠。

## 我的默认工具箱

以后写一个没有特殊约束的普通 Web 应用，可以默认从这里开始：

```text
Vite
JavaScript + JSDoc，必要时 TypeScript
VanJS
VanX
原生 CSS 和 CSS variables
fetch + AbortController
URL + History API
IndexedDB / SQLite
Vitest
Playwright
按需引入专业库
```

使用顺序也很自然：

```text
声明式写起来舒服
→ VanJS

数据结构和列表变复杂
→ VanX

某个位置需要精确控制
→ 直接操作真实 DOM

进入专业领域
→ 交给专业库
```

这不是一套封闭的框架，而是从轻到重、随时能返回浏览器的平台组合。

## 最后留下几句话

VanJS 可以成为默认工具，但不需要成为信仰。

静态 HTML 足够时，不用响应式；服务端返回 HTML 更简单时，可以用服务端模板或 htmx；工作明确要求 React 时，直接用 React；专业渲染问题出现时，让专业引擎接管。

但当问题只是：

> 我想写一个普通、长期可用的 Web 应用，没有特殊组织约束，应该从哪里开始？

答案完全可以是 VanJS。

不是因为它能假装自己拥有大框架的一切，而是因为大多数个人项目根本不需要那一切。

不是因为所有复杂度都不存在，而是因为真正的复杂度应该在出现时，被隔离到真正复杂的那个局部。

不是因为生态没有价值，而是因为自己的项目不必替大型组织的问题买单。

最终最值得长期深化的仍然是：

```text
JavaScript
DOM
HTML
CSS
浏览器 API
状态与数据建模
网络和存储
性能与调试
```

VanJS 的优雅就在于，它站在这些东西旁边，而不是站在它们前面。

> 大多数大型 Web 产品只是很多普通功能长期叠加，并不是每一层都存在神秘的前端技术。真正变态的客户端引擎，个人通常不会做，也没有必要提前为它设计。既然如此，就用一个自己能看懂、能掌控、随时可以回到原生的工具，把真正想做的东西做出来。
