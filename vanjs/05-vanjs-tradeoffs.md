# VanJS 的设计取舍

> 记录选用 Van 核时认下的边界与用法纪律。这些是设计衍生的注意点，不是实现硬伤。  
> 工程默认见 `../WEB-DEVELOPMENT-PREFERENCES.md`；城规见 `../ARCHITECTURE-WORLDVIEW.md`。

## 1. 核选了什么

Van 核大约百余行，刻意保持：

- **真 DOM** + 标签函数，无 VDOM、无编译器。
- **`state` 是值盒子**：用引用相等（`!==`）判断变不变；换 `.val` 才通知。
- **依赖收集 + 微任务批更新**：读过的 state 自动订上；`derive` 先收敛，再换绑定 DOM。
- **绑定重跑即可**：默认 `replaceWith` / `remove`，不做列表差分引擎。

换来的是：源码可读、行为可预期、缺点写在说明书上。  
富对象/细粒度列表不进核；需要时再考虑官方扩展 vanX，或自己用写法规避。

## 2. 因此认下的边界

| 取舍 | 含义 | 用法上怎么接 |
|---|---|---|
| 只认引用替换 | `arr.push` / `obj.x = 1` 不刷新 | 当不可变：赋新数组/新对象；大对象拆多个 `state` |
| 不做列表差分 | `() => ul(items.val.map(...))` 会整段重建 | 小表可接受；数据多先分页/懒加载；真要一屏狂滚再虚拟列表（与框架无关） |
| 允许手搓 DOM | 可与绑定混用 | 自定规矩：视图只派生；事件里只改 state，不改已绑定节点 |
| 绑定读到即订阅 | `() =>` 里读了什么就依赖什么 | 少读无关全局，避免一行重绘被旁路状态拖着跑 |
| 无正式 Context | 不提供跨树隐式注入 | 模块级 state、显式传参、薄「辖区」自行组织 |
| 卸载靠 `isConnected` 懒清理 | 不提供重生命周期 API | 大块卸挂时自己别死握旧引用即可 |
| 核保持极小 | 虚拟列表、完整路由/SSR 不进核 | 分页优先；SSR 看 Mini-Van；专业交互用纯 JS 库 |

## 3. 写法纪律（由取舍推出）

1. **状态当不可变用**：增删改都产出新 `.val` 再赋回。
2. **视图纯派生**：`state` / `() => ...` / `derive` 驱动 DOM；不与命令式改同一片已绑定 DOM。
3. **派生收窄**：筛选、计数放 `derive`；绑定函数里只读真正需要的盒子。
4. **输入策略单一**：受控就 `value: state` + 事件写回 state；不要 DOM 与绑定抢 `value`。
5. **`derive` 慎改上游**：可做轻副作用（如同步存储），避免在里面连环改一串 state。
6. **列表先瘦 DOM**：默认整表 `map` + 分页；不上虚拟列表除非可测到卡顿且必须同屏长滚。

## 4. 和「UI = f(state)」的关系

Van 是：**用 JS 函数组合真 DOM + 细粒度状态绑定**。  
有人比作「JS 里的 Flutter」——仅在「代码搭 UI、数据驱动」这层像；实现上没有 Widget/Element 对拍树，更近「反应式 + 真 DOM」，不是 Flutter 的移植。

## 5. 一句话

**Van 用最小模型换透明；缺点已知、用纪律接住。**  
大列表首先是少挂 DOM 的问题，不是换反应式库的问题。
