# Text Vault 设计规格

> 2026-08-30 认证修订：界面只输入一个主密码。浏览器使用不同盐值分别派生本地包裹密钥和 256 位后端认证凭证；包裹密钥不离开浏览器，Go 后端只接收派生凭证并保存其 SHA-256 哈希，不再设置或询问独立访问口令。

## 1. 目标

Text Vault 是一个单用户、搜索优先、客户端加密的通用记录工具。第一版优先做到可日常使用：打开后快速搜索，选择条目，编辑纯文本，明确手动保存，并在桌面与临时使用的手机浏览器之间同步密文。

系统采用类似 Windows 记事本的保存心智模型：应用内部的一切编辑都立即进入统一的内存工作状态，只有明确执行一次全局“保存”才会把全部变化提交到服务器。界面不提供单条保存、保存工作区或其他保存方式，不要求用户判断该保存什么。程序不承诺恢复尚未全局保存的修改，也不以模糊状态掩盖保存失败。

长期方向是“数据—查询—视图”架构：条目可逐步增加属性，查询产生对象集合，多个视图展示同一集合。第一版只开放纯文本列表和编辑器，但底层对象格式不得阻碍以后增加表格、看板、日历、关系和附件。

## 2. 第一版范围

第一版包括：

- 单用户保险库的创建、解锁与锁定。
- 浏览器端加密和解密，服务器只存储密文。
- 一个条目一份自由纯文本；条目无需用户填写标题。
- 解锁后在前端内存中实时全文搜索。
- 创建、选择和编辑条目，并使用唯一的全局保存动作提交所有变化。
- 多个搜索标签；当前查询可以固定到底部标签栏。
- 桌面端左侧搜索结果、右侧内容编辑器、底部标签栏。
- 手机端顶部搜索栏、中间列表或内容、底部标签栏。
- 应用内的正文、属性、搜索索引、查询结果和工作区状态实时同步到统一内存仓库。
- 全局保存时一次提交全部已变化对象与工作区。
- 使用 revision 检测并发修改，禁止静默覆盖。
- 明确显示已保存、未保存、保存中、保存失败和冲突状态。
- 密文数据目录可直接备份和迁移。

第一版不包括：

- 自动保存正文、自动草稿或崩溃恢复。
- 离线编辑或离线阅读保证。
- 附件、Markdown 预览、富文本编辑。
- 属性编辑器、查询语言、表格、看板、日历或关系图。
- 自动填充浏览器密码。
- 多用户、分享、权限系统、AI 和服务端全文搜索。
- 服务端定时任务、提醒或自动化。

## 3. 技术架构

项目位于 `apps/text-vault`。

前端使用无需构建的 JavaScript 与 VanJS。它负责统一内存对象仓库、客户端加密、全文搜索、查询标签、编辑交互和所有视图渲染。内存对象仓库是解锁会话期间唯一的当前工作状态；编辑器、搜索和视图都读写它，不各自保留互不一致的副本。

依赖选择遵循“原生优先、专业小轮子优先于重复造轮子”，而不是极端追求零依赖。浏览器原生 API 足够清楚可靠时直接使用；格式解析、模糊搜索、代码编辑或文档查看等细分问题，如果成熟的小型库能显著降低错误率和维护成本，则允许引入。每个运行时依赖必须用途单一、体积与收益相称、固定精确版本、本地托管、许可证可接受、支持按需加载，并通过自有接口隔离以便替换。不得仅为风格统一重写成熟算法，也不得引入包管理链条和大型框架来解决小问题。

后端使用 Go 标准库与纯 Go SQLite 驱动。它负责登录会话、密文对象 API、revision 条件写入、SQLite事务提交、静态资源服务及必要的备份导出。前端资源和SQLite引擎通过编译打入单个 Go 可执行文件。

生产部署由一个 Go 二进制、一个数据目录及 HTTPS 反向代理组成。服务器不安装 Node.js，也不执行前端业务逻辑。

逻辑分层如下：

```text
UI 与视图
    ↓
查询与工作区状态
    ↓
内存对象仓库
    ↓
加密边界
    ↓
密文同步 API
    ↓
SQLite密文存储
```

每一层只依赖其下一层的公开接口，避免 UI、加密算法和存储格式相互耦合。

## 4. 通用对象模型

持久化的内容都表示为带身份和版本的数据对象，包括条目、工作区、查询和视图。搜索结果、分组和统计属于可重新计算的派生数据，不持久化；悬停、焦点、输入法组合状态等瞬时界面状态也不持久化。

解锁后的逻辑对象采用带版本号的通用格式：

```js
{
  schemaVersion: 1,
  id: "随机且不可预测的 ID",
  kind: "entry",
  text: "自由纯文本",
  properties: {},
  createdAt: "ISO-8601 时间",
  updatedAt: "ISO-8601 时间",
  revision: 1
}
```

第一版中 `kind` 固定为 `entry`，`properties` 保持空对象且不在界面显示。保留它们是为了以后增加可选属性、查询和视图时不必替换对象身份或迁移正文模型。

标题不是必填数据。列表摘要可从正文第一段或匹配片段派生，不写回条目。

以后增加的保存查询和视图也使用对象身份，但必须具有各自明确的 schema，不将任意配置塞进条目正文。

## 5. 密文存储模型

服务器数据目录为：

```text
data/
├── text-vault.db
└── blobs/              # 后续附件，第一版不存在
```

SQLite的 `metadata` 表保存口令派生参数、被包裹的数据密钥和全局 generation；`objects` 表保存每个对象当前生效的密文版本；`object_versions` 保存可回退的历史密文。正文、属性、查询词、当前选择及其他工作区内容均在密文 envelope 内。

服务器可见对象数量、密文大小、修改时间和 revision 等同步元数据，但看不到正文、属性、搜索词或工作区内容。该元数据泄露是第一版明确接受的边界。

全局保存以一个SQLite写事务提交发生变化的密文对象。服务器在事务内校验批次基准 generation 及所有对象 revision，写入历史版本和当前版本，最后增加全局 generation。任一校验或写入失败时整个事务回滚，不发布部分结果。

## 6. 密钥模型

创建保险库时，浏览器生成随机保险库数据密钥。用户口令通过带独立盐值的密码密钥派生流程生成解锁密钥；解锁密钥只负责包裹数据密钥。每个对象使用数据密钥、唯一随机 nonce 和带认证加密分别加密。

这样修改口令只需重新包裹数据密钥，无需重新加密全部对象。具体算法、参数、格式版本和迁移规则在实现计划中根据当前浏览器支持与权威安全建议确定，不允许自行设计密码算法。

明文和解开的数据密钥只存在于已解锁页面的运行内存。锁定时清空应用仓库、搜索索引、编辑器和密钥引用。实现不得声称 JavaScript 能保证物理内存被安全擦除；安全目标是停止应用继续持有和展示这些引用。

## 7. 搜索与查询演进

第一版解锁后获取全部条目密文，在浏览器中解密，并建立简单内存对象仓库。全文搜索对正文执行大小写不敏感的匹配，返回条目 ID 与匹配摘要。

目标规模为日常数百到一千条，设计上支持约一万条普通文本记录。第一版无需数据库全文索引。列表必须虚拟化或限制实际渲染节点数，避免结果数量直接扩大 DOM。

如果搜索计算开始影响交互，可在保持查询接口不变的情况下依次增加 Web Worker、增量倒排索引和持久化加密缓存。不得为了尚未出现的规模提前引入服务器明文索引。

未来查询层接受自由文本条件和结构化属性条件，输出稳定的对象 ID 集合；列表、表格、看板和日历只消费查询结果，不复制条目数据。

## 8. 统一内存与全局保存语义

解锁后，前端将所有已加载对象组成统一内存仓库。编辑器中的每次输入立即更新对应内存对象，并增量更新搜索索引。因此尚未提交服务器的修改、新建条目和属性变化必须立刻可以被搜索、查询和其他视图看到。

切换条目、切换查询标签、返回列表和调整布局只是在同一个内存状态上改变视角，不发生保存、不丢弃编辑，也不弹出确认。再次打开条目时显示同一份内存对象的当前内容。

前端内部维护变化对象集合及各对象的基准 revision，以避免每次保存重新上传未变化对象；这是实现细节，不在界面暴露。用户只看到一个全局状态：

- 已保存：内存状态与服务器已提交状态一致。
- 未保存：内存中存在任意变化。
- 保存中：全局提交正在进行。
- 保存失败：整批提交未成功，内存变化仍然保留。
- 冲突：服务器已基于其他状态产生新提交，本地变化未被覆盖。

界面只提供一个全局“保存”动作。执行保存时：

1. 固定当前内存状态的提交视图，避免加密过程中继续输入造成状态混淆。
2. 收集所有发生变化的条目、查询、视图与工作区对象。
3. 分别加密这些对象，形成一个批次，并携带当前服务器提交版本。
4. 服务器校验全部版本并以单次逻辑提交发布整个批次。
5. 提交成功后，仅当内存没有提交开始后产生的新变化时显示“已保存”；否则仍显示“未保存”。

如果只编辑了一个条目，批次自然只包含该条目及发生变化的工作区对象；用户不需要选择“保存当前”还是“保存全部”。保存失败时所有编辑继续留在内存，显示持久可见的错误并允许再次执行同一个全局保存动作。页面刷新或进程终止后，最后一次成功保存之后的变化可能丢失，这是产品明确行为。

## 9. 离开保护

应用内部导航不因未保存状态而被阻止。只有将离开当前内存环境的动作需要保护：页面刷新、关闭浏览器标签页、跳转到外部页面，以及锁定或退出保险库。

页面刷新和浏览器关闭时注册标准 `beforeunload` 保护，使用浏览器原生离开警告。锁定和退出由应用确认是否放弃全部未保存变化。产品不得承诺浏览器一定显示警告：iOS 杀后台、系统终止进程及部分浏览器策略可能绕过事件。界面通过持续可见的全局未保存状态帮助用户形成离开前保存的习惯。

## 10. 工作区与标签

工作区快照包含：

```js
{
  schemaVersion: 1,
  activeTabId: "...",
  tabs: [
    {
      id: "...",
      query: "...",
      selectedEntryId: "...",
      listScrollTop: 0
    }
  ],
  splitRatio: 0.36,
  theme: "warm-paper"
}
```

标签切换、搜索词、滚动位置和分栏调整会立即改变统一内存工作区，并立即影响当前界面。工作区与其他变化一起由唯一的全局保存动作持久化；刷新后只恢复最后一次成功保存的状态。

搜索词不得写入 URL、浏览器历史、localStorage 或分析日志。URL 最多包含无语义且不可预测的对象 ID；第一版可以完全不以 URL 表达工作区。

## 11. 界面行为

桌面端维持三部分：左侧搜索框和结果列表、右侧纯文本编辑器、底部横向标签栏。左右分栏比例可拖动，保存后进入工作区快照。

手机端不缩小桌面双栏：顶部为搜索、返回、保存及状态；中间一次只显示结果列表或当前条目；底部为可横向滚动的搜索标签栏。选择结果进入内容，返回时恢复该标签的查询、结果和内存滚动位置。

视觉采用暖白纸张、深棕文字、暗红强调、细分隔线和克制阴影，借鉴锤子便签的工具感。正文、IP、域名、命令和凭据内容优先保证可读与可复制，装饰不得牺牲密度或触摸目标尺寸。

## 12. 错误与冲突

所有网络和持久化操作均具有明确的全局状态，禁止仅用短暂 Toast 表达关键失败。条目和标签上不得出现“单独保存”控件或要求用户理解提交批次的状态。

revision 冲突时整批停止保存，保留完整的当前内存状态，并获取服务器提交摘要。第一版至少提供导出当前未保存状态、查看服务器版本和放弃本地变化三个安全动作。不得自动合并或覆盖。

解密认证失败视为数据损坏、密钥不匹配或格式不受支持，不把残缺内容交给上层。单个对象失败时隔离该对象并显示对象 ID，其他可解密对象仍允许只读查看；在问题处理前禁止会扩大损坏的批量写入。

## 13. API 边界

第一版 API 只需要：

- 创建或读取保险库头。
- 列出密文条目及 revision。
- 获取单个或批量密文条目。
- 批量读取密文对象。
- 校验版本并逻辑原子地提交一批密文对象和工作区。
- 创建、验证和注销单用户会话。
- 导出完整密文数据包。

API 不接受全文查询，不理解条目属性，也不返回解密内容。所有写接口限制请求大小、校验对象 ID 格式并采用同源会话与 CSRF 防护。公网部署必须位于 HTTPS 后。

## 14. 备份与恢复

运行数据不提交到 `msi-void` Git 仓库。项目提供明确的 `.gitignore`，并将 `data/`、SQLite临时文件、备份包和本地配置排除。

备份使用SQLite在线备份能力生成一致的数据库快照；后续存在附件时，再与加密 `blobs/` 一起归档。不得在程序运行时只复制主数据库文件而忽略WAL状态。恢复测试必须证明：在空目录启动新实例、放入备份、使用原口令解锁后，条目与工作区均可读取。未经验证的多份复制不视为可靠备份。

## 15. 测试与日用验收

必须覆盖：

- 加密后服务器文件不包含已知正文和搜索词。
- 正确口令可解锁，错误口令不产生部分明文。
- 创建、编辑、执行唯一的全局保存并重新解锁后内容一致。
- 编辑内容后不保存即可切换条目和标签，再返回时内存内容保持不变。
- 未保存的新建和修改内容立即出现在全文搜索及查询结果中。
- 界面不存在单条保存、保存工作区或“保存全部”等额外概念，唯一按钮只标为“保存”。
- 存在未保存状态时，刷新和离开页面注册浏览器原生警告；锁定和退出由应用确认。
- 放弃全部修改可恢复最后一次服务器提交状态。
- 保存失败不清除编辑器内容，也不显示已保存。
- 两个客户端基于同一 revision 保存时，后提交者得到冲突。
- 全局保存同时提交所有变化；任一版本校验失败时服务器不发布部分结果。
- 工作区只恢复最后一次全局保存的标签、查询和布局。
- 桌面左右布局和手机列表/内容切换均可操作。
- iPhone 浏览器中输入框不触发页面整体缩放，键盘出现时保存与返回仍可达。
- 密文备份可以在空实例中恢复。

第一版达到“可日用”的标准是：应用内部任意切换都不丢失内存修改，修改能实时参与搜索，没有静默丢失已保存数据，没有静默覆盖冲突，全局未保存状态始终可见，并能从实际备份完成一次恢复演练。

## 16. 后续扩展边界

后续功能按独立增量加入：

1. 可选属性编辑和结构化查询。
2. 保存的查询与表格、看板、日历视图。
3. 条目关系和双向链接。
4. Markdown 阅读视图。
5. 附件对象与按需下载解密。
6. 可选的本地加密草稿恢复。

这些扩展复用对象仓库、查询接口、加密边界与密文 API。任何需要服务端读取数据的提醒、自动化或协作功能都必须重新评估客户端加密的安全边界，不能作为无影响的小功能加入。
